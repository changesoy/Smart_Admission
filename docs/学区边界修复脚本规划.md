# 学区边界修复脚本规划（v1：L1 顶点对齐 + L2 交点裁剪）

> 状态：M1、M1.1、M2 已实施，M3 的 L1 与 L2（交点裁剪）均已实现；候选仍为 `reports/` 下的 dry-run 产物，未写入工作副本。
> 定位：对 [学区边界临时规划.md](./学区边界临时规划.md) 第三节的落地细化，把"按修复记录生成候选"变成可验收的第一版。
> 本文件只形成规划：不修改业务代码、不新增依赖、不改动学区数据。
> **修改已有学区一律按第十六节的标准模式执行**（整界贴线，不在骨架线上只取两个点）。

## 一、目标与非目标

### 目标

1. **问题可编号**：任何待修复的边界问题都能被 `check:zones` 以稳定 ID 列出，并给出面积、位置与判定依据。
2. **修复可回放**：人工确认的规则写成修复记录，脚本按记录生成候选数据，重复执行结果一致。
3. **候选可验收**：修复前后的差异、面积变化、地址归属变化都能被自动核对，人工只需判断"这个变化是否符合政策"。

### 非目标（v1 明确不做）

- 真正的求差裁剪（L3）：需要多边形布尔运算引擎，v1 不引入。
- 投影插点：L1 不产生新坐标；L2 只插入"环边 × 骨架线"的交点，不做任意投影或加密。
- 自动决定"该用哪条骨架线"：选线由人工给出。
- 孔洞与 MultiPolygon 编辑：当前数据中没有，v1 遇到即报错而非猜测。
- 坐标规范化（如统一到 1e-7 度）：与 v1 的精确匹配逻辑冲突，推迟到 v1 之后单独评估。
- 内置网页编辑器、PDF/四至文字一键生成边界。

## 三、核心设计决定

| 编号 | 决定                                                              | 理由                                                                                                                        |
| ---- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| D1   | 问题用确定性 `issueId` 编号                                       | 修复记录要指向具体问题；时间戳、自增序号都不可复现                                                                          |
| D2   | 学区环用**坐标锚点**寻址；L2 用**交点坐标**（`cuts`）定位替换范围 | 环下标在连续执行后整体偏移，第二批记录必然错位；交点由"环边 × 骨架线"求得、以坐标写入记录，执行时按坐标就近定位，不依赖下标 |
| D3   | L1 只**复用已有顶点**；L2 只新增两个交点，中间整段复用骨架线顶点  | 保证幂等、避免碎点；交点数量与位置由记录固定，不随执行顺序变化                                                              |
| D4   | 批内**原子执行**，默认 dry-run，失败计数并退出非零                | 否则"检查通过"可能只是"坏记录被跳过"                                                                                        |
| D5   | 检查**不依赖求交引擎**                                            | 用线段相交、点在环内、共边偏移方向三类判定即可定位问题；块面积用网格估算，不引入多边形裁剪                                  |
| D6   | 动作只有两种：L1 顶点对齐、L2 交点裁剪                            | 覆盖当前主要问题；L1 无需裁剪，L2 只按交点截取折线，仍不引入多边形布尔运算                                                  |
| D7   | 单块冲突面积 ≥ 250 m² **必须单列汇报**                            | 大小问题混在一张清单里会让大冲突被淹没；阈值只设这一处，不再另设忽略阈值                                                    |
| D8   | 争议按四至文本详细度采信；同指一条界线时不适用                    | 文本是政策依据；两侧都写"以××路为界"时属结构问题，不应拿来比谁写得更细                                                      |

### D5 的判定方式（避免引入依赖）

- **重叠存在性**：两环的边存在非端点相交，或一方的顶点严格落在另一方环内。
- **窄条 vs 缝隙**：对"近似共边但顶点不一致"的区段，用有向边的左右侧判定参考顶点落在内侧还是外侧——内侧为重叠带，外侧为缝隙；两者都以"最大偏离距离"作为宽度指标。

因此 v1 不需要多边形裁剪库，也不需要 Turf；`issueId` 中的哈希只用于标识，不参与几何计算。

### 冲突分块与面积口径（硬性）

- **块**：同一对学区之间连通的一片冲突区域。两侧边界存在交点时，按相邻交点切分；只有包含关系、没有交点时，整片包含区域记为一块。
- **面积**：v1 用块自身包围盒（该块的交点，以及两侧落在块内的顶点）内的固定网格统计"同时在两环内"的格数估算，默认 1 m；格子数超过 40 万时逐级放大到 2/4/8…（上限 64 m）。输出 `areaM2`、`areaMethod`、`cellSizeM`。
- 包含类块的包围盒取"被包含环上落入对方内部的顶点段（含两端邻点）"，而不是直接相交整对包围盒；后者会把两侧相距很远的部分一并框入，导致面积严重高估。
- 只有重叠产生面积块；**缝隙不产生块**，按宽度单独汇报，不参与面积分级。
- 这是估算值，不是精确相交面积；精确面积要等 L3 的裁剪引擎。估算不确定度按"块边界长度 × 格距"写入 `areaUncertaintyM2`。
- **汇报分级**：`areaM2 ≥ 250` → `reportLevel: "required"`，必须在报告与摘要中单列，不得被任何数量上限折叠；`areaM2 ≥ 200` 且 `< 250` → `reportLevel: "near-threshold"`，提示人工复核；其余 `info`。
- 250 m² 是唯一阈值，不另设"小于多少就忽略"的隐藏门槛；细小问题保留在报告中，只降低展示优先级。
- 阈值附近不得因为估算误差漏报：落在 `near-threshold` 的块一律按"可能需要汇报"处理。

### 争议裁决规则（硬性）

用于两校边界冲突且**几何上无法判定该归谁**的情形，按以下顺序处理，前一档成立时不进入下一档：

1. **同指一条具名界线**：两侧 `boundaryText` 都写明以同一道路/铁路/河流为界（如南关"东界…迎春西路"与迎春"沿迎春西路向北"）。此时以该界线为准，**不比较文本详细度**；这是结构问题，交给 L1/L2 解决。
2. **指向不同地物或不同区段**：比较两侧 `boundaryText`，采信更详细的一侧。详细度按以下可计算指标综合排序：是否给出起止关系（"自…沿…至…"）、有效具名地物数、东南西北四界是否齐全、是否说明排除或分段、原文长度。
3. **详细度相当、一侧缺失、或只有"沿线/周边"**：不自动采信，登记 `needsRuling`，人工裁定后才允许生成修复记录。

脚本只输出两侧原文并排对照与上述指标，**不自动判定谁更详细**。采信结果写入记录的 `ruling` 字段，保留两侧摘录，便于回答"当时凭什么选了这一侧"。

## 五、修复记录格式

一个批次一个文件，批次 = 一次人工核对的结论。

```json
{
  "schemaVersion": 1,
  "batchId": "2026-10-zones-l1l2-01",
  "createdAt": "2026-10-22",
  "baseRelease": "v2025.1",
  "baseZonesSha256": "sha256:…",
  "featuresSha256": "sha256:…",
  "note": "2025 年四至统计表复核后的第一批",
  "expectedAddressChanges": [
    { "addressId": "addr_0123", "from": ["zone_002"], "to": ["zone_033"] }
  ],
  "records": [
    {
      "recordId": "r-001",
      "issueId": "overlap:zone_002|zone_033:7c1e",
      "zoneId": "zone_002",
      "action": "snap-shared-boundary",
      "anchors": { "from": [117.02, 36.19], "to": [117.03, 36.2] },
      "referenceZoneId": "zone_033",
      "guards": { "maxDeviationM": 3 },
      "expected": { "areaDeltaM2": [-50, 50], "pointCount": 41 },
      "ruling": {
        "basis": "same-feature",
        "note": "两侧四至均以灵山大街为界，以该线为准，不比较详细度"
      },
      "evidence": {
        "excerpt": "南界：灵山大街",
        "sourceName": "泰山区 2025 年义务教育学校地址及四至范围统计表",
        "sourceUrl": "https://…"
      },
      "confirmedBy": "…",
      "confirmedAt": "2026-10-22"
    },
    {
      "recordId": "r-002",
      "issueId": "shared-edge:zone_006:8b2d",
      "zoneId": "zone_006",
      "action": "replace-with-feature",
      "featureId": "bf_yingchun_road",
      "cuts": {
        "from": [117.0312, 36.2004],
        "to": [117.0391, 36.2088]
      },
      "guards": { "maxCutOffsetM": 3 },
      "expected": { "areaDeltaM2": [-200, 0], "pointCount": 38 },
      "evidence": {
        "excerpt": "东界：迎春路",
        "sourceName": "…",
        "sourceUrl": "https://…"
      },
      "confirmedBy": "…",
      "confirmedAt": "2026-10-22"
    }
  ]
}
```

### 字段说明

| 字段                          | 必填     | 说明                                                                          |
| ----------------------------- | -------- | ----------------------------------------------------------------------------- |
| `schemaVersion`               | 是       | 记录格式版本，v1 为 `1`                                                       |
| `batchId`                     | 是       | 与文件名一致，全局唯一                                                        |
| `baseRelease`                 | 是       | 记录针对的数据基线；与当前数据不符时整批拒绝执行                              |
| `baseZonesSha256`             | 是       | 记录所依据的 `zones.geojson` 哈希；版本号可能对应多份内容，必须锁到具体字节   |
| `featuresSha256`              | L2 必填  | 骨架线文件哈希；骨架线不随版本发布，靠它保证批次可追溯                        |
| `note`                        | 否       | 本批次的背景说明                                                              |
| `expectedAddressChanges`      | 否       | 已预判的地址归属变化；未在此登记的归属变化视为错误                            |
| `records[]`                   | 是       | 至少一条                                                                      |
| `recordId`                    | 是       | 批内唯一，用于排序与报错定位                                                  |
| `issueId`                     | 是       | 来自 `check:zones` 报告；该问题已不存在时视为记录过期                         |
| `zoneId`                      | 是       | 被修改的学区                                                                  |
| `action`                      | 是       | `snap-shared-boundary` 或 `replace-with-feature`                              |
| `anchors`                     | L1 必填  | 被修改环上的两个端点坐标，必须与目标环顶点完全相等且各只出现一次              |
| `referenceAnchors`            | L1 可选  | 参照环上的对应端点；省略时取 `anchors`（两侧共用同一坐标）                    |
| `referenceZoneId`             | L1 必填  | 提供顶点序列的邻区                                                            |
| `featureId`                   | L2 必填  | 骨架线 ID                                                                     |
| `cuts`                        | L2 必填  | "环边 × 骨架线"的两个交点坐标；中间整段复用骨架线折线，两侧学区应写同一对坐标 |
| `guards.maxDeviationM`        | L1 必填  | 替换区段的最大允许偏离，取自报告实测值，不设默认值                            |
| `guards.maxCutOffsetM`        | L2 必填  | 交点距环、距骨架线的最大允许偏移；用于容纳人工描边与 OSM 中线的误差           |
| `expected.areaDeltaM2`        | 是       | 允许的面积变化区间（修复后减修复前），兜底防"改错方向"                        |
| `expected.pointCount`         | 是       | 修复后该 zone 的顶点数                                                        |
| `ruling`                      | 争议必填 | `basis`: `same-feature` / `text-detail` / `manual`；附两侧原文摘录            |
| `evidence`                    | 是       | 复用 zones 现有的 `sourceName` / `sourceUrl` 字段名，附原文片段               |
| `confirmedBy` / `confirmedAt` | 是       | 人工确认责任人与日期                                                          |

### 记录校验规则

1. `recordId`、`batchId` 唯一；`action` 取值合法；必填字段齐全。
2. `zoneId`、`referenceZoneId`、`featureId` 必须存在。
3. `issueId` 必须出现在最近的检查报告中；报告里已无此问题 → 记录标记为过期并报错。
4. 同一批次内，同一 `zoneId` 的两条记录锚点区间不得重叠。
5. `anchors` 的两个坐标在该 zone 环上各自只出现一次；出现多次时拒绝执行并提示人工改写。
6. L2 的两个 `cuts` 必须分别落在骨架线与目标环上（距离 ≤ `guards.maxCutOffsetM`），且不得落在同一条环边上。

## 六、骨架线格式（L2 依赖）

v1 只收录试点记录实际用到的线，不追求覆盖全部道路。

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "properties": {
        "featureId": "bf_yingchun_road",
        "name": "迎春路",
        "lineType": "道路",
        "geometryStatus": "ready",
        "sourceType": "osm",
        "accuracy": "约 5 米",
        "note": "以道路中心线为界"
      },
      "geometry": {
        "type": "LineString",
        "coordinates": [
          [117.03, 36.2],
          [117.04, 36.21]
        ]
      }
    }
  ]
}
```

约定：

- `featureId` 稳定且被记录引用，不使用名称作为主键（同名道路分段要拆成两个 ID 并在 `note` 中说明）。
- `geometryStatus` 取值 `ready` / `needsTrace` / `needsRuling`；只有 `ready` 的线可被 L2 引用。
- 线的坐标顺序即存储顺序；L2 不以下标寻址，而是用记录中的两个交点坐标在线上就近定位，中间整段按存储顺序取用。因此批次必须提供 `featuresSha256`，且交点必须落在同一条连续区段上。
- v1 只支持 `LineString`，遇到其他类型报错。
- **不随发布版本发布**：不加入 `config.js` 的 `dataPaths`、不进入 `data/releases/` 与 manifest。构建脚本只复制 `current.json` 和当前版本目录，因此该文件不会被静态服务暴露；批次记录用 `featuresSha256` 固定其所依据的骨架线版本。

## 七、动作定义

### L1 `snap-shared-boundary`（顶点对齐）

用途：两个相邻学区共用一条边，但两侧顶点不一致，产生窄条重叠或缝隙。

前置条件：

1. 两个 zone 同 stage、同 year。
2. `anchors` 在被修改环上精确存在且各只出现一次；`referenceAnchors`（省略时取 `anchors`）在参照环上同样精确存在且唯一。两侧锚点**不必是同一坐标**：现有数据里多数相邻学区各自描边，找不到完全相同的共享顶点。
3. 被修改环上取两锚点之间**不跨越环首点**的子路径；参照环上两锚点之间有两条子路径，取与被替换子路径偏离更小的一条，因此记录里的 from/to 方向不产生歧义。
4. 被替换的子路径不包含环的首点（`ring[0]`），以保证环起点不变。
5. 偏离度只统计两条子路径的**内部顶点**（锚点之间的连接边由两端锚点直接承担）；被替换路径内部顶点到参考路径的垂距、参考路径内部顶点到被替换路径的垂距，均不得超过 `guards.maxDeviationM`。

执行：把被修改环上两锚点之间的子路径替换为参照环对应子路径的顶点序列；起点/终点不同时，由两端锚点直接连接，仍然不产生任何新坐标。锚点坐标完全相同时退化为经典的"共享顶点对齐"。

### L2 `replace-with-feature`（交点裁剪）

用途：把一段人工描边整段替换为已标定骨架线（道路/铁路/河流中线）。典型场景是学校某一界本应完全贴着骨干道路，但人工描边只是大致沿路。

前置条件：

1. 骨架线存在且 `geometryStatus = ready`，几何类型为 `LineString`。
2. 记录的 `cuts.from` / `cuts.to` 是"环边 × 骨架线"的两个交点；两个交点都必须落在骨架线上、且各自到目标环的距离不超过 `guards.maxCutOffsetM`（容纳人工描边与 OSM 中线的误差）。
3. 两个交点必须在骨架线上位于同一条连续区段（按存储顺序可从一个走到另一个），且中间至少隔一段折线。
4. 两个交点在目标环上不能落在同一条环边上：否则环上没有可替换的弧段，v1 拒绝执行。
5. 两个交点把目标环分成两条弧；取与骨架线偏离更小的那条弧作为被替换弧，另一条弧整段保留。记录无须指明是哪一条弧，执行时按偏差自动选择。

执行：用 `[交点A, 骨架线中间顶点…, 交点B]` 替换被替换弧的内部顶点，两条弧的取舍与书写方向都以保持原有绕向为准（反向环会反转骨架线段顺序）。交点本身是唯一新增坐标；北界、南界与道路的交点之外，中间每一个顶点都直接复用骨架线顶点，因此修好后该界**逐点等于道路中心线**，两侧学区共用同一串坐标。

与 L1 的区别：L1 要求两侧有共享顶点、结果只能是"取其一"；L2 允许两侧都不在中线上，各自吸附到同一条骨架线，替换后两侧逐点共用整段骨架线顶点，而不是只对齐两个端点。

### 两种动作共同的不变量

- 只修改 `geometry`，`properties` 逐字段相等。
- 环依然闭合（首尾坐标相等）、顶点顺序仍为同一绕向、无自相交。
- 未涉及的学区、未涉及的坐标完全不变；`FeatureCollection` 中 feature 顺序不变。
- 修复后面积变化与顶点数必须落在 `expected` 内，否则该条记录失败。

## 八、执行流程

### 阶段 A：预检（全部通过才进入执行）

1. 批次文件 schema 校验、`batchId` 唯一性。
2. `baseRelease` 与当前生效版本一致，且 `baseZonesSha256` 与当前 `zones.geojson` 字节哈希一致（防止同名版本对应不同内容）。
3. 每条记录按第三节规则校验，并检查 `issueId` 是否仍存在于最新检查报告。
4. 同一 zone 的多条记录锚点区间互不重叠。
5. 定位校验：L1 的 `anchors` 在环上精确存在；L2 的两个 `cuts` 在环与骨架线上都能就近定位（偏移 ≤ `guards.maxCutOffsetM`），且不落在同一条环边上。

任一条失败：**不产出候选**，列出全部失败原因，退出码 2。

### 阶段 B：执行

1. 按 `(zoneId, recordId)` 稳定排序。
2. 逐条执行替换，执行后立即做几何守卫（闭合、自相交、面积变化、顶点数）。
3. 全部完成后统一计算地址归属变化。

### 阶段 C：输出

| 产物                                                | 内容                                                                                                                        |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `reports/repairs/<batchId>/zones.candidate.geojson` | 候选数据，未写入工作副本                                                                                                    |
| `reports/repairs/<batchId>/diff.json`               | 每条记录：面积前后与差值、顶点数变化、变化区域 bbox；L2 另含 `featureId`、`cutOffsetM`（交点实际偏移）与 `ringStartChanged` |
| `reports/repairs/<batchId>/address-changes.json`    | 地址点归属变化；未在批次 `expectedAddressChanges` 中登记的视为错误                                                          |
| 控制台摘要                                          | 成功条数、失败条数、面积变化合计                                                                                            |

退出码：`0` 全部成功；`2` 任一记录失败或存在未登记归属变化。dry-run 也输出候选，便于人工查看后决定是否写入。

### 阶段 D：写入工作副本（人工触发）

仅在人工核对候选与差异后执行 `--write`，随后：

1. 更新 `data/zones.geojson`（仍只改 `geometry`）。
2. 在 `zones_history.json` 追加一条变更记录，说明依据与涉及学区。
3. 走现有发布流程生成新快照并切换生效版本；已发布快照不原地修改。

## 九、检查入口 `check:zones`

v1 的检查项：

| 检查项         | 判定                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| 环闭合         | 首尾坐标严格相等                                                             |
| 自相交         | 任意两条非相邻边存在非端点相交                                               |
| 退化           | 环顶点数少于 3 或面积为 0                                                    |
| 面积重叠       | 同 stage、同 year 的两环存在非端点相交，或一方顶点严格在另一方环内           |
| 冲突块         | 同一对学区的冲突按相邻交点切分，估算每块面积并标记 `reportLevel`             |
| 共边顶点不一致 | 近似共边的区段两侧顶点集合不同；按左右侧判定为重叠带或缝隙，给出最大偏离距离 |
| 结构提示       | 出现 MultiPolygon 或内环（v1 不支持编辑，仅提示）                            |

输出：

- `reports/zones/issues-<日期>.json`：机读问题清单，含 `issueId`、类型、涉及学区、宽度、定位点、`areaM2`、`areaMethod`、`cellSizeM`、`areaUncertaintyM2`、`reportLevel`。
- `reports/zones/issues-<日期>.geojson`：问题图层，可直接在 QGIS 或 geojson.io 中查看位置。
- 控制台摘要：先列 `reportLevel = "required"` 的冲突块（单块面积 ≥ 250 m²，逐条列出，不折叠），再列其余问题的分类计数。

`issueId` 规则：`<类型>:<zoneId 排序后用 | 连接>:<哈希>`，哈希基于问题定位坐标（四舍五入到 1e-7 度后拼接）计算，保证同一问题跨次运行编号稳定；哈希只用于标识，不参与几何计算。

v1 中 `check:zones` 只报告、不阻断（退出码 0）；阈值与阻断规则待报告数据积累后再定。

## 十六、标准修改模式（所有已有学区通用）

**原则：一条界只要政策文本指明以某条具名道路/铁路/河流为界，就把这条界整段换成该地物的中心线。** 先用"环边 × 骨架线"求出这条界与地物的两个交点，两个交点之间**逐点复用骨架线顶点**；不要只在骨架线上挑两个点再把原来的描边连回去——那样两端仍会残留在道路两侧，形成斜向回插或向外顶出的狭长块。

### 步骤

| 步骤 | 操作                                                                                                                                                 | 判据 / 产物                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1    | 在 `check:zones` 报告中定位问题，按 D8 判定该界是否"两侧同指一条具名界线"                                                                            | 同一具名地物 → 可直接脚本化；详细度相当且指向不同地物 → `needsRuling`，人工裁定后再动       |
| 2    | 标定骨架线：从 `data/streets.geojson` 取该地物中心线写入 `data/boundary_features.geojson`，`geometryStatus` 置 `ready`；同名分段拆成两个 `featureId` | 线未标定（`needsTrace`）时不得开工；不得用道路端点或人工猜测的直线顶替                      |
| 3    | 求交点：分别取该界两端**与骨架线的交点**（环边与线的最近交点），作为 `cuts.from` / `cuts.to`                                                         | 交点必须落在骨架线上、距环 ≤ `guards.maxCutOffsetM`；不能用道路自身的起止点代替             |
| 4    | 写修复记录：`action: replace-with-feature`，填 `cuts`、`guards.maxCutOffsetM`、`expected`                                                            | 先空跑一次把实测面积差与顶点数填进 `expected`，不凭感觉估                                   |
| 5    | 相邻学区共用同一对 `cuts` 与同一个 `featureId`                                                                                                       | 两侧环在这些顶点上**坐标完全相等**，不再各自描边                                            |
| 6    | `npm run repair:zones` dry-run，看 `diff.json` 与控制台                                                                                              | 该界端点之间必须等于 `[交点, 骨架线中间顶点…, 交点]`；该对学区的冲突块（块面积/缝隙）应归零 |
| 7    | 人工核对候选后 `--write`，再走发布流程                                                                                                               | 已发布快照不原地修改；写入前保留 `reports/` 候选与差异                                      |

### 验收时怎么确认"真的贴线"

- 在候选环上找到南、北两个交点，取出它们之间的顶点序列，应与骨架线对应区段**逐点相等**（不是"距离很小"）。
- 两条相邻学区的环在同一区段上取出的坐标序列应完全相同。
- `check:zones` 对这对学区的 `overlap-containment`、`shared-edge-overlap`、`shared-edge-gap` 不再出现 ≥ 250 m² 的块。
- 只贴了一部分界的情形必须显式说明原因（另一段所属地物尚未标定），不得用"最近点连线"蒙混。

### 边界情形

- **一个交点落在环的顶点上**：`featurePosition` 会把骨架线位置吸附到整数下标，中间顶点仍取严格介于两交点之间的部分，结果不变。
- **环的书写方向与骨架线相反**：按环的前进方向书写替换段，必要时反转骨架线段顺序，保证绕向不变。
- **两个交点落在同一条环边上**：环上没有可替换弧段，v1 直接拒绝，需检查交点是否求错。
- **该界由两段不同地物组成**（如北段道路、南段铁路）：拆成两条记录，分别用各自的骨架线与交点；两条记录的交点必须重合在同一点。
- **界上有不可忽略的凸出/凹入**（政策文本本身如此）：不属于本模式，回到 D8 第 2、3 档人工裁定，不自动裁剪。
