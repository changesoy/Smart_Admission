# 评审稿：学区边界「吸附骨架」方案

> 用途：提交外部评审。本文只描述方案、现状事实与已做的决定，不含代码实现细节。
> 项目：泰安市泰山区 / 岱岳区 / 泰山景区「智慧入学信息公示平台」，数据以 GeoJSON 维护。
> 日期：2026-10-26

---

## 一、要解决的问题

平台需要给每所学校维护一份「学区范围」多边形。当前 `zones.geojson` 里的边界是**按官方四至文本手绘**的，存在两类顽固问题：

1. **相邻学区对同一路口取了不同位置**，形成 15 处重叠/空隙块（最大 1516 m²），每块都要人工裁定。
2. **边界与真实道路不贴合**：手绘线可能偏离道路中心线数米到数十米，视觉上和官方「以某路为界」的表述不一致。

过去两轮的做法是「先修路网，再对已有边界做局部修补」：

- L1 顶点对齐（把边界顶点吸附到道路已有顶点）；
- L2 交点裁剪（在两线交点处切掉原环的中间段，整段复用道路顶点）。

这套修补能压掉冲突块，但本质是**在错误的手绘骨架上打补丁**：每新增一所学校、每条新路，都要再来一轮。现决定改为**从四至文本直接派生边界**。

## 三、方案：四层结构

| 层            | 职责                                            | 产物                                  | 是否改数据     |
| ------------- | ----------------------------------------------- | ------------------------------------- | -------------- |
| L0 交点       | 已有：路-路交点 + 插入顶点                      | `data/intersections.geojson`          | 已定稿，不再改 |
| L0.5 逻辑图   | 把交点与端点组织成「节点 + 边」的路网图         | `reports/road-graph.json`             | 只读           |
| L1 四至段序列 | 把四至文本拆成 `{along, from, to}` 的可执行序列 | `data/zone_specs/<zoneId>.json`       | 新增           |
| L2 派生环     | 在图上沿指定道路找路径、拼闭合环                | `reports/zone-rings/<zoneId>.geojson` | 只读           |
| L3 门禁       | 溯源、闭合、自交、共用段一致性                  | 扩展现有校验脚本                      | 只读           |

### 3.1 逻辑图（L0.5）：双层模型

这是方案唯一需要仔细设计的部分。

**物理层**：196 个交点保持不变，几何仍是路网自己的顶点。
**逻辑层**：把 A 类 15 组近邻节点**各收缩为一个逻辑节点（anchor）**，其余物理节点不再作为图的节点，只保留作显示用途。

逻辑节点数量：196 − 34 + 15 = **177**。

节点示例：

```json
{
  "id": "gn_ix_rail_001_road_001_1",
  "kind": "cross",
  "anchorCoord": [117.0, 36.0],
  "anchorReason": "节点类型 cross > tee；实体等级 铁路 > 主干道路；距组中心最近",
  "members": [
    {
      "nodeId": "ix_rail_001_road_001_1",
      "roadId": "rail_001",
      "part": 0,
      "vertex": 412
    },
    {
      "nodeId": "ix_rail_001_road_001_2",
      "roadId": "road_001",
      "part": 0,
      "vertex": 88
    }
  ]
}
```

边示例：

```json
{
  "id": "ge_road_034_88_93",
  "roadId": "road_034",
  "name": "灵山大街",
  "from": "gn_A",
  "to": "gn_B",
  "fromVertex": 88,
  "toVertex": 93,
  "geometry": [
    [117.0, 36.0],
    [117.0, 36.0]
  ],
  "lengthM": 512.4
}
```

三条规则：

1. 边的端点必须落在成员顶点上；同一 `roadId` 内相邻两个逻辑节点之间才建边。
2. 同一道路上的两个成员若被收缩到同一 anchor（同路重复交点的典型情况），**不建自环**，记录 `collapsedSelfLoop` 并从图中跳过。
3. 每条边必须能回答「我是哪条路的第几号顶点到第几号顶点」，这是 L3 溯源门禁的依据。

### 3.2 环的几何取点

**已定**：环经过合并路口时，取**该道路自己的顶点坐标**，不用 anchor 坐标。

理由：

- 环 100% 由路网顶点组成，可逐点溯源；
- 相邻两个学区若共享同一段路，引用的是同一批边，几何天然逐点相同，不需要再对齐；
- anchor 只承担「这是同一个路口」的身份与引用，不进入几何，避免因收缩产生折角。

### 3.3 四至段序列（L1）

每校一个 spec：

```json
{
  "zoneId": "zone_034",
  "school": "南关中学",
  "ring": [
    {
      "along": "road_034",
      "from": "gn_A",
      "to": "gn_B",
      "text": "南至灵山大街"
    },
    { "along": "road_061", "from": "gn_B", "to": "gn_C", "text": "西至迎春路" }
  ]
}
```

录入方式（已定）：**半自动抽取 + 人工复核**。

- 脚本从 `boundaryText` 切分「东临 / 南至 / 西界 / 北靠」候选句，把路名匹配到 `roadId`，并列出该路上所有逻辑节点，按原文方位给出候选 `from/to`；
- 人工确认起止节点、方向、非路名参照（如「东临迎春学校」「优山美地西邻路」「泰山区界」）；
- 草稿放 `data/zone_specs/draft/`，确认后才参与派生。

### 3.4 派生算法（L2）

对每个 spec：

1. 在该 `roadId` 的边子集上求 `from → to` 的路径；
2. 找不到路径 → 登记 `needsRuling`，不猜；
3. 同一段路存在两条及以上走法（环线、多 part、并列支路）→ 输出候选并标 `ambiguous`，交人工选；
4. 相邻段在交点处首尾相接，接点坐标取该道路自身顶点；
5. 拼环后校验：闭合、自交、面积为正、顶点溯源率；
6. 与现行 `zones.geojson` 逐段计算偏差（p50 / p90 / max），只报告。

### 3.5 验收标准

| 检查           | 阈值                                     |
| -------------- | ---------------------------------------- |
| 闭合误差       | ≤ 1 m                                    |
| 顶点溯源率     | 100%（每个顶点可答出 roadId + 顶点下标） |
| 自交           | 0                                        |
| 与现行边界偏差 | p90 > 10 m 需人工确认                    |
| 多解           | 必须标 `ambiguous`，不自动选             |

### 3.6 已定的其他规则

- **铁路、河流全部允许作为边界段**：四至写「西至京沪铁路」就沿铁路走；图里不区分要素类型，但路径只在 spec 指定的一条线上走，不会自动绕行。
- **切换段只能发生在已有点上**：贯通近失 82 条目前不是节点，四至若要求在无节点处拐弯，只能登记 `needsRuling` 或先补节点。
- **不插值**：环的顶点只复用路网顶点。
- **默认 dry-run**：所有脚本默认只读，显式 `--write` 才落盘。
- **已发布版本不可变**：几何变更走新版本目录 + `data/current.json` 指针切换。

## 五、备选方案与取舍

**备选 A：继续人工修补现有边界（L1 顶点对齐 + L2 交点裁剪）**

- 优点：改动小，已跑通两对试点。
- 缺点：每次新增学校/道路都要重来一轮；冲突根因（同一路口两个坐标）无法根除。**已放弃。**

**备选 B：只做增量替换（偏差超阈值的段才替换）**

- 优点：风险小、易审。
- 缺点：新旧接头处可能出现微小错位；相邻学区可能一半新一半旧，共用段一致性无法保证。**未采用。**

**备选 C：完全自动从四至文本生成（不做人工复核）**

- 缺点：非路名参照无法可靠解析，误生成风险高。**未采用。**

## 六、风险与未决项

1. **区界依赖未裁定**：「至泰山区界」的段目前只能沿用现行边界；OSM 与 DataV 两套区界 p50 差 323 m，直接决定这些段的形态。是否应把「区界段」从本轮派生中剥离，单独作为下一阶段？
2. **贯通近失 82 条**：图连通性可能在某些支路处断开；需先出「14 个学区里哪些四至段落在不同连通分量」的清单，避免到 L2 才发现闭不上。
3. **同路自环收缩**：收缩后是否会丢失真实的连接关系（例如同一道路两侧各有一个节点、收缩后变成单个点）？
4. **多解与方向**：单行道、环线、MultiLineString 段内可能存在两条等长路径；仅靠「最短」是否足够？
5. **全量替换的迁移风险**：14 个学区一次性替换，是否需要保留「旧边界对照视图」与回滚机制？
6. **图中的要素等级**：是否需要在边契约中携带道路等级/宽度，供后续视觉分级（主干线金色、支路灰色）与验收使用？

## 九、2026-10-26 本轮已落地（含过程记录）

### 9.1 结论：官方原文不能直接当真

原文存在错别字与复制粘贴过时文件两类问题。本轮实例：

- zone_006（六中新校区）东界、zone_031（凤台学校初中部）西界，原文均写「双龙河」；
- 环上 20 多个连续顶点实际贴在**唐王河**（偏差 0~23.4 m），双龙河在该纬段 670~1036 m 之外；
- 唐王河本身在路网里缺线，四至里却被三所学校引用（凤台小学西界、花园校区东界、小井小学）。

因此确立规则：**以现状环逐顶点反查「最贴近的具名要素」为准，原文只作对照**；
原文与环冲突且环连续贴合时，采信环、把裁定写入 `zones.geojson` 的 `boundaryRulings`，
`boundaryText` 保留官方原文不动。

### 9.3 段序列的形态与三态来源

`data/zone_specs.json` 里每所学校给出「从某路口出发 → 沿某要素 → 到下一路口 → …… → 回到起点」的闭合序列，
每段的 `from` / `to` 首尾相接，最后一段回到第一段起点。

每段标来源三态：

- `text`：原文点名该要素，环也连续贴它；
- `ring-snap`：原文没点名或点名错了，环连续贴该要素 → 以环为准；
- `legacy`：容差内没有任何具名要素 → 沿用旧环，待补线。

原文点名但环未贴合的登记进 `textGaps`；段端点离最近真实路口超过 25 m 的登记进 `needsRulingSteps`。
这两个清单就是下一轮「先补线 / 先裁定」的待办来源。

抽取口径（本轮四次返工后固化）：

1. **探针取线段中点，不取顶点**。手绘环顶点稀疏，逐顶点会漏掉「整段贴着某条河」的边
   （zone_006 西界迎春路曾因此被误判为未贴合）。
2. **短段按长度吸收，不按段数吸收**。相邻路口的横穿道路会让环切出 40~180 m 的碎段；
   这类碎段（< 200 m）并入其前一段，被吞并要素写进该段 `absorbed`，不静默丢。
   早期按「段数 < 3」吸收，把迎春路 711 m（只有 2 段）也当成碎段吞掉了，已改。
3. **无名段不吸收**。`legacy` 是真实缺口，必须留在表里。
4. **内建契约自检**：闭合、线段不重不漏、段间接缝 0 m；任一不成立直接拒绝写盘。
