## 四、新脚本方向（本次会话的结论）

### 4.1 问题

v1（`repair-zones.mjs`）是“逐对学区打补丁”：为每一对冲突学区写 L1/L2 动作记录。
路网标定完成后，更划算的是“按四至定义生成边界”，这样新增学区几乎不费力。

### 4.2 分层模型

| 层 | 职责 | 计划产物 |
| --- | --- | --- |
| L0 交点图谱 | `roads.geojson` 64 条线两两求交（含河流/铁路），生成具名交点 | `data/intersections.geojson`（Point + `{id, roadA, roadB}`） |
| L1 四至解析 | `boundaryText` 拆成段序列：`{along: 路名, from: 交点id, to: 交点id}` | `data/zone_specs/<zoneId>.json` |
| L2 边界构建 | 在路网图上按段序列找路径、拼闭合环，写出候选 `Polygon` | `reports/` 候选，人工确认后回填 |
| L3 校验 | **沿用** `check-zones.mjs` 作回归门禁，不改动 | 现有报告格式 |

要点：

- 学区边界交点不是独立概念，**它就是路-路交点**；现有 15 个冲突块本质是
  “相邻学区对同一交点取了不同位置”。
- 段序列格式必须可人工编辑（四至文本里有“东临”“南关中学东界”“优山美地西邻路”
  这类非路名参照，无法自动解析）。
- 同名路多次相交需消歧（交点 id 带序号），否则段序列有歧义。

### 4.3 已识别的短板（决定推进顺序）

1. 21 条清单道路无线源 → 相关段序列走不通（谢过城街阻塞第 3 对学区）。
2. 13 条 `estimated` 示意线偏差大 → 生成的环会歪。
3. 四至文本非路名参照 → 必须人工指定节点。
4. OSM 实测：21 条缺线只命中 1 条（大众桥），13 条示意线命中 **0** 条；
   OSM 在泰安城区对支路/街巷基本空白，**不能作为补线主力**。

## 七、坑与硬约束

1. **行尾口径**：`.gitattributes` 规定 `data/** text eol=crlf`。写数据文件必须
   `JSON.stringify(...).replace(/\n/g, "\r\n")`，否则清单 bytes/sha256 会失配。
2. **发布快照不可变**：日常只改 `data/*.json` 工作副本；改已发布版本必须显式说明
   （本次 `b5d2a0b` 属破例修坏账）。
3. **`zones_history.json` 行尾**：2026.10.6–10.9 已在 `b5d2a0b` 修复，`check:release` 全通过。
4. **PowerShell 中文**：提交信息走 `git commit -F <临时文件>`，不要用 `-m` 直接写中文。
5. **Overpass API**：必须带 `User-Agent`，否则 406；bbox `36.0,116.9,36.35,117.35`。
6. **前端不校验 manifest**：只读 `current.json` → `releases/<版本>/`，所以清单问题不影响网站。
7. **`reports/` 与 `MERGE_PLAN.md` 均被 gitignore**，不入库。
